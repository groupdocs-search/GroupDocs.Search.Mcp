# 26.10.1 — explain an unwritable index folder, document `--user` for Docker on Linux

## What changed

- **An index folder the server cannot write now fails with the fix, not a raw exception.** Before
  creating, adding to, updating or removing from an index, the server checks that the index folder can
  be written. If not, the response (`isError: true`) reads: *"The index folder '…' is not writable by the
  server process. In Docker on Linux the container runs as a non-root user, so a host folder you own is
  read-only to it: add --user "$(id -u):$(id -g)" to docker run, or mount a writable folder at /index and
  set GROUPDOCS_MCP_INDEX_PATH=/index. …"* Previously the agent received
  `System.UnauthorizedAccessException: Access to the path '/data/.groupdocs-search-index' is denied`.
- **README:** new section *Linux: run the container as your user*, including the literal-number form
  (`"--user", "1000:1000"`) for MCP client JSON configs, which do not run a shell.
- Unit test for the unwritable-folder path (38 unit tests).

## Why

The first CI run of the integration suite against the published 26.10.0 image failed 20 of 31 tests on
`ubuntu-latest`. The image runs as uid 1654; on a Linux host a bind mount keeps its host owner, so the
runner's temp folder — and any folder a Linux user owns — is read-only inside the container, and the
default index location `/data/.groupdocs-search-index` cannot be created. Docker Desktop on Windows and
macOS does not enforce bind-mount ownership, which is why local verification passed.

Search is hit harder than the other products because building an index is a write even when the user
only wants to search. The same cause affects every family image that writes into `/data` (Parser's
`extract_images` docker tests fail on it); that is tracked in `docs/backlog-and-issues.md`.

## Migration impact

None for callers. Linux Docker users who saw the access-denied error add `--user "$(id -u):$(id -g)"`
(or the numeric form in JSON configs). Windows and macOS are unaffected.
